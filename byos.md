# Bring Your Own Supabase (BYOS) Architecture

**BYOS (Bring Your Own Supabase)** allows organizations using FastestCRM to connect their own dedicated Supabase project. When enabled, 100% of company-specific business data, heavy queries, and database functions run on the customer's own Supabase infrastructure.

---

## 💡 How Edge Functions Work Without Deploying Them to Customer Supabase

A common question is: **"If BYOS only provisions tables in the customer's Supabase, how do Edge Functions work?"**

### **Answer: Remote Client Injection Architecture (`getOrgAdminClient`)**

1. **Hosted Edge Gateway**: 
   - All Edge Functions (e.g. `get-public-form`, `ai-lead-score`, `enrich-lead`, `trigger-automation`) are maintained and deployed on FastestCRM's central serverless platform.
   - Customers **do NOT** need to install, configure, or host Edge Functions or Deno runtime environments on their own Supabase project.

2. **Dynamic Remote Connection**:
   - When an Edge Function executes, it passes `companyId` to `getOrgAdminClient(companyId)`.
   - The function inspects `byos_connections`, decrypts the customer's BYOS `supabase_url` and `service_role_key`, and instantiates a remote Supabase client.

3. **Direct Database Offloading**:
   - Every `.from('leads')`, `.from('invoices')`, `.from('forms')` PostgREST query generated by the Edge Function is executed **directly against the Customer's BYOS Database API**.
   - All SQL processing, filtering, index scans, and data storage occur on the customer's BYOS PostgreSQL hardware.

4. **In-Database PL/pgSQL Helper Functions**:
   - Native PostgreSQL helper functions (such as `update_updated_at_column()` triggers and `pg_trgm` search extensions) are automatically created inside the customer's BYOS `public` schema during the initial SQL migration execution.

## 📊 Detailed Responsibilities: BYOS vs. Main Supabase

### 1. **Data & Heavy Database Lifting (Customer's BYOS Supabase)**
All heavy CRM operations, core business records, and customer-specific transactions run directly on your BYOS PostgreSQL CPU, memory, and storage:

- **Core Business & Industry Records**: `leads`, `leads_saas`, `leads_real_estate`, `leads_healthcare`, `leads_insurance`, `leads_travel`, `lead_history`
- **Sales & Catalog**: `lead_statuses` (and `company_lead_statuses`), `products`, `real_estate_properties`
- **Finance & Payments**: `invoices`, `invoice_items`, `invoice_payments`, `quotations`, `quotation_items`
- **Marketing & Automation**: `forms`, `form_responses`, `landing_pages`, `automations`, `tasks`, `notifications`, `push_subscriptions`
- **AI & Workflows**: `ai_employees`, `ai_caller_logs`, `agentic_workflows`, `agentic_workflow_runs`, `calendar_bookings`, `calendar_connections`, `booking_pages`
- **Indexes, Constraints & Joins**: All JSONB queries, full-text searches, sorting, pagination, and cascade operations run on your BYOS database.

---

### 2. **Edge Functions & Serverless Logic (`getOrgAdminClient`)**
Our serverless Edge Functions dynamically target your BYOS Supabase:

- When an Edge Function executes, it calls `getOrgAdminClient(companyId)`.
- If BYOS is active, the function decrypts your BYOS credentials and executes all database queries, inserts, and updates directly against your BYOS Supabase instance.

---

### 3. **Main Platform Supabase (Lightweight Control Plane)**
Our central platform database only retains lightweight identity, licensing, and integration authentication infrastructure:

- **Authentication**: `auth.users` & session tokens.
- **Licensing & Billing**: `companies` (subscriptions, feature flags) & `wallets` / `wallet_transactions`.
- **BYOS Credentials**: `byos_connections` (encrypted API keys and connection status).
- **Global Accounts & Permissions**: `profiles` & `user_roles`.
- **Integrations & API Keys**: `integration_api_keys` — Third-party service API keys (Gemini, OpenAI, Tata Smartflo, Vobiz, WhatsApp credentials) are saved on the Default Platform Supabase, tied to `user_id`. This allows central Edge Functions and AI services to securely authenticate integration APIs on your behalf.

## ⚡ Technical Mechanics

### 1. **Client-Side Data Routing (`useOrgClient`)**
The frontend utilizes the `useOrgClient` hook to dynamically route database queries:
- **BYOS Enabled**: Intercepts requests and queries the customer's Supabase instance (`orgClient`).
- **BYOS Disabled**: Queries the default platform Supabase instance.

### 2. **Resilient Schema Engine**
BYOS automatically maintains schema compatibility across database versions with dual-table and host-aware fallbacks:
- **Pipeline Statuses**: Host-aware primary selection for `lead_statuses` and legacy `company_lead_statuses`.
- **Calendar & Meetings**: Host-aware routing for `calendar_bookings` and `calendar_events`.
- **Form Builder**: Tiered compatibility support for `created_by_id`/`created_by`, `name`/`title`, and `status`/`is_active`.

## 🔄 Migration & Lifecycle

- **Automated Setup**: Connecting BYOS executes `BYOS_MIGRATION_SQL` on the target Supabase to provision all tables, indexes, and RLS policies.
- **Data Syncing**: Existing platform leads, products, and records are synced into the customer's BYOS instance upon connection.
- **Safe Disconnect**: Disconnecting BYOS migrates all org-scoped data back to FastestCRM servers seamlessly.


Note: BYOS is just a way to use custom Supabase. Most of the heavy lifting shall be moved to this BYOS Server so that we can save cost on the Main Server. 
- So we just need to make sure that the code is compatible with both BYOS and Main Server. This is a multi-tenant application, and we need to make sure that the code is compatible with both BYOS and Main Server. 
- The main application will always run on our Main Supabase Server with all Authentication, Licencing, Users used from default Supabase.
- So the BYOS Enabled company will have their own Supabase database for their leads, invoices, products, etc and most of the heavy lifting shall happen there.
-BYOS Server will have similar tables as the Main Server. This will reduce code complications and simply just use there supabase. (We will use the same schema and logic as much as possible.)


IF BYOS is not enabled for a company, then all the data will be stored in our Main Supabase Server like before. (We will keep the code compatible with both.)
